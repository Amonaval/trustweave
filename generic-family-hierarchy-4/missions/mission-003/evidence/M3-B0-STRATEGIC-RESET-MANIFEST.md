## Repository diagnosis captured in B0

- Architecture is not starting from zero: `core/`, `capabilities/`, `verticals/` and `components/shared/` already provide meaningful seams. M3-A remains the implementation evidence base.
- Engineering verification is comparatively mature: GitHub Actions, source gates, Playwright, mutation guards, RPC/security audits, disposable migration replay and evidence reports already exist. The missing layer is mission-scoped orchestration and authority, not another test framework.
- AI execution remains human-orchestrated: no durable mission controller currently owns branch/worktree creation, PR/check feedback, bounded retry/repair, independent review and evidence closure across sessions.
- Knowledge authority is ambiguous: the repository currently contains 63 root Markdown files, divergent root/`docs/product` mirrors, and historical current/next-mission language. `ARCHIVE-INDEX.md` previously described a much smaller root set, so drift is measurable.
- The project exposes 200 npm scripts. Future automation should compose a small mission-specific gate manifest from existing checks rather than create another monolithic validation chain.
- The migration tree is structurally healthy through 121 and remains immutable; M3-B0 did not alter migrations.

## Founder decisions required before B1/B2 become binding

The recommended defaults are:

1. **Organization:** approve six accountable roles (Mission Lead, Architecture Governor, Builder, Independent Reviewer, Verification Agent, Release & Knowledge Agent) with Security/Data/UX/Performance/Accessibility as risk-triggered specialist lenses rather than permanent agents.
2. **Human gates:** retain mandatory human approval for constitution changes, strategic scope/vertical changes, privacy/security risk acceptance, destructive or irreversible production data actions, new recurring infrastructure commitments and production release at the current maturity.
3. **Execution control plane:** use Git + mission branch/worktree + GitHub PR/checks + commit-SHA evidence as the durable control plane for B5; do not introduce a dedicated multi-agent framework yet.
4. **Runtime safety:** maintain a disposable QA/release-candidate database/environment separate from protected staging/production for migration/destructive certification.
5. **Knowledge policy:** approve the two-axis authority model and single-copy canonical-document rule, followed by B3 archival/compaction of divergent mirrors and historical session diaries.
6. **Maturity target:** recognize TrustWeave as L1 today and target L2 next. Do not optimize for L3-L5 until the B6 experiment demonstrates that L2 reduces founder intervention without weakening evidence.

If these defaults are accepted, B1/B2 can be promoted from proposed authority to accepted governance without inventing additional standalone documents for the approval matrix, maturity model, scorecard or document authority model; those responsibilities are intentionally consolidated into the three governing artifacts.
