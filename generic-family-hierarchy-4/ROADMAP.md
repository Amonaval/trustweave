# TrustWeave — Roadmap

**Updated:** 2026-09-23  
**Roadmap type:** outcome/stage roadmap, not fixed-date feature contract

Canonical long-term direction: `docs/product/00-FOUNDER-DIRECTION-AND-12-MONTH-STRATEGY.md`.

## Current priority — FCA-L1

Prove:

> **Can MPF Pune East use TrustWeave as a credible real Community product rather than merely a showcase?**

Immediate sequence:

1. audit the previously observed pilot blockers against the latest source/runtime;
2. fix only what remains concretely broken;
3. make MPF Pune East data/content representative or full-fidelity enough for real use;
4. validate President/committee + ordinary-member critical journeys;
5. show/use it with a small real pilot group;
6. classify feedback into blocker / repeated friction / useful later / noise;
7. stop and re-select.

Majestique Marbella runs in parallel as the Residential proving network. Fix real-use blockers there; do not independently recreate shared Community functionality.

## 0–3 months — flagship adoption and habit

### Month 1 — readiness

- MPF Pune East full/representative data onboarded and ready.
- Majestique Marbella Residential product ready.
- critical admin/member journeys are understandable and reliable.
- existing capability is discoverable without Founder narration.

### Months 2–3 — return usage

- increase real engagement and recurring workflows in both flagships;
- let real requirements drive depth;
- prioritize **Generic + Easy + Impactful** requirements;
- favor complete lifecycle, notifications/deep links, media, directory/profiles, groups/events/posts, membership/governance and Residential operations that users actually choose.

Stop optimizing for feature count.

## Months 3–4 — commercial productization

As adoption evidence improves:

- groom final product name/domain/identity;
- professionalize demo/public/contact/request-pilot path;
- define onboarding/support process;
- form pricing/packaging hypotheses;
- clarify privacy/trust story and commercial operating path.

Company registration, paid tiers, domains/services or any other chargeable commitment remain explicit Founder decisions.

## Months 4–6 — repeatability + Preschool/School

Goal: prove TrustWeave can add networks/verticals without becoming custom software.

- attempt additional Community/Residential networks with falling engineering effort;
- target roughly 10–20 additional network trials only if onboarding is repeatable;
- begin Preschool/School as the next serious proving vertical when flagship stability allows;
- reuse identity, roles, relationships, actions, consent, media, events, notifications and governance primitives;
- keep genuinely School-specific behavior explicit.

Small playgroups/preschools are preferred early learning partners because feedback cycles can be faster.

## Months 3–9 — AI-powered value and evidence-triggered hardening

Parallel work, only when it serves real usage:

### AI

Prioritize context-rich jobs such as:

- “Who can help?” trusted discovery;
- admin/operator action copilots;
- meeting/event/follow-up orchestration;
- institutional/community memory;
- engagement/missing-information intelligence;
- safe messy-data onboarding;
- natural-language operations over governed capabilities.

Reject generic chatbot work with no measurable job improvement.

### Hardening

Continuously address real security, privacy, correctness, reliability and measured performance needs.

Do not add Kafka, Jenkins, queues, microservices, paid Supabase/Vercel tiers or other infrastructure from calendar pressure. Use:

> **Measure → identify bottleneck → optimize existing system → scale cheaply → add infrastructure only when justified.**

## Months 7–9 — business-network expansion

Explore evidence-backed small-business/multi-location use cases such as salons, automobile/dealer/service networks, franchises and professional/business associations.

Invest when buyer pain is clear, platform reuse is high and willingness-to-pay evidence exists.

## Month 12 — startup-readiness aspiration

Aspirational portfolio:

- 10+ small-business networks/use cases;
- 10+ preschools/playgroups;
- 1 larger school;
- 3+ Residential networks;
- 3+ Communities/Associations;
- 300+ families;
- 5,000+ members.

Counts are secondary to sustained usage, repeatable onboarding, reusable capability growth, willingness to pay, credible trust/reliability and declining Founder support per network.

## Protected / parked workstreams

These remain valuable but are not current execution authority:

- Network Activation Autopilot;
- D12 database recovery/reconstruction;
- broad architecture convergence;
- Autonomous Company maturity beyond what real delivery requires;
- broad connected QA/reliability programs;
- School implementation before its stage gate;
- Business vertical implementation without buyer/design-partner pull;
- broad federation/intelligence expansion without local-network value;
- marketplace/add-on ecosystem before repeated extension demand.

A parked item becomes active only when real evidence or a concrete blocker re-selects it.

## Permanent execution rules

- one active priority;
- roughly 20–30% effort for 70–80% alpha/pilot impact-learning;
- Generic + Easy + Impactful;
- Adopt → Compose → Extend → Build;
- smallest evidence set that proves the outcome;
- default 1–5 coherent commits;
- no broad QA/recovery by habit;
- no automatic database mutation;
- no additional cost without explicit Founder warning/consent;
- source proof, runtime proof and pilot validation stay distinct.

## Portfolio re-selection

At each stop condition ask:

1. what did real users/admins actually do?
2. what blocked adoption/trust?
3. what repeated requirement can become shared capability?
4. what manual Founder/admin/developer work repeated?
5. what is the highest-value next step per complexity?
6. should we deepen, simplify, automate, commercialize or expand?

The backlog supplies options. **Evidence selects the mission.**
