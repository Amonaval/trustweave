# G1.3 — Neutral Network & Membership Contracts

**Date:** 2026-08-25  
**Status:** IMPLEMENTED IN SOURCE / CLOSED AS NON-BREAKING ARCHITECTURE MISSION / DEPLOYED DB SMOKE REQUIRED

## Objective

Create the neutral TypeScript seam for network identity/context and user↔network membership without changing Family UI, Family RPC names, `network_memberships` columns, `family_members`, or existing Family membership behavior.

This round also repairs the Playground/Launch Control drift discovered during G1.2 verification: code could know `contribute.branch_intake` while an older deployed Supabase feature registry did not, causing `Unknown feature key: contribute.branch_intake` when the Platform Owner toggled the Playground checkbox.

## Classification

### CORE — neutral contracts

New `core/network/contracts.ts` owns:
- `NetworkMembershipRole`;
- `NetworkMembershipStatus`;
- `NetworkIdentity`;
- `NetworkResourcePolicy`;
- neutral `NetworkMembership`;
- `ActiveNetworkContext`;
- generic network-admin role evaluation.

The core contract deliberately contains no `member_id`, `family_members`, Family, Alumni, kinship or institutional profile-link semantics.

### FAMILY VERTICAL — legacy membership adapter

New `verticals/family/network/membership-adapter.ts` owns the exact historical `get_my_networks()` transport row, including `member_id`.

That field is explicitly classified as a Family profile-claim compatibility leak because the current database column points to `family_members`. The adapter can convert the legacy row to the neutral core membership contract while separately exposing the Family profile link when a Family caller actually needs it.

Alumni is not forced onto this link model.

### LEGACY FACADE — behavior preserved

`lib/remote.ts` now exposes:
- `fetchMyNetworkMemberships()` — neutral runtime contract;
- `fetchMyNetworks()` — unchanged historical Family-shaped facade for existing UI;
- `NetworkMembership` — compatibility alias to the historical Family transport row.

`fetchNetworkSettings()` now consumes the neutral membership path internally. Existing `FamilySwitcher` and `NetworkApp` callers remain untouched.

`AuthUser` now has `membership_role` as the neutral field while preserving `family_role` as a compatibility alias with the same runtime value.

`NetworkSettings.membership_role` now uses the neutral core role type.

## Database behavior

G1.3 does **not** rename/drop/migrate:
- `network_memberships`;
- `network_memberships.member_id`;
- `family_members`;
- `get_my_networks()`;
- `set_active_network()`;
- any Family claiming/join RPC.

The Family leak is isolated in TypeScript rather than hidden behind a fake generic schema.

## Playground feature-key regression fix

### Root cause

`FounderLaunchConsole` renders the current TypeScript Family feature catalog. A deployment that has newer frontend code but has not applied the matching Supabase migrations can therefore show a feature key that is absent from `platform_feature_flags`. The backend correctly rejects attempts to toggle an unknown key.

### Fix

1. `supabase/migrations/044_g1_3_feature_catalog_integrity.sql`
   - requires the S3-A1 backend from migration 043 before repairing `contribute.branch_intake`;
   - idempotently inserts only missing Family feature-registry rows;
   - idempotently inserts only missing Playground rows;
   - never overwrites existing Platform Owner rollout/Playground choices.
2. `FounderLaunchConsole`
   - no longer treats a missing backend feature row as enabled by default;
   - disables controls for a code-known/database-missing feature;
   - displays `Database update required` instead of letting the user hit `Unknown feature key`;
   - bulk Playground show/hide operates only on keys confirmed by the backend.
3. `validate:g1.3`
   - verifies all 23 Family catalog keys are represented in the reconciliation migration;
   - verifies the UI drift guard exists;
   - verifies G1.3 does not alter the membership schema/RPC.

## Architecture gate correction

The older G1.1 source gate previously matched any import path containing `verticals/`, which accidentally rejected a Core module importing another Core contract under `core/verticals/`. The gate now resolves import paths and rejects only dependencies into the explicit root `verticals/` implementation tree.

The architectural rule is unchanged: Core may depend on Core contracts; Core may not import Family or Alumni implementations.
