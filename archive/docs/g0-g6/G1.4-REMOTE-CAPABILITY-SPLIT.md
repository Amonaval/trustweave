# G1.4 — Remote Capability Split Behind Compatibility Facade

**Date:** 2026-08-25  
**Status:** IMPLEMENTED IN SOURCE / CLOSED AS NON-BREAKING ARCHITECTURE MISSION / NORMAL DEPLOYED SMOKE RECOMMENDED

## Objective

Reduce the monolithic `lib/remote.ts` safely by moving only transport that is already proven to be Core/shared runtime, while preserving every historical `lib/remote.ts` export and every deployed RPC/table name.

G1.4 is a physical dependency-boundary change, not a product behavior change.

## Classification before movement

### Moved — Network Context capability

New: `capabilities/network-context/remote.ts`

Moved:
- `fetchMyNetworkMemberships()`
- `setActiveNetwork()`

Why shared: user↔network membership and active-network switching are Core semantics established in G1.3.

Important compatibility rule: the neutral transport does not model or expose `member_id`. The historical Family-shaped `fetchMyNetworks()` remains in `lib/remote.ts` with the Family membership adapter.

### Moved — Launch Runtime capability

New: `capabilities/launch-runtime/remote.ts`

Moved:
- Playground feature read/write transport;
- effective platform-feature retrieval;
- platform Launch Control retrieval;
- pilot target retrieval;
- rollout audit retrieval;
- feature/bundle rollout writes;
- feature-announcement read/seen transport.

Why shared: these are rollout/runtime mechanics rather than Family-domain behavior.

`get_platform_family_targets` and the compatibility type name `PlatformFamilyTarget` remain unchanged because G1.4 does not rename backend contracts merely for naming cleanliness.

### Moved — Platform Ownership capability

New: `capabilities/platform-ownership/remote.ts`

Moved:
- list Platform Owners;
- add owner by email;
- remove owner;
- owner audit retrieval.

Why shared: Platform Owner authority governs the whole runtime, not Family kinship semantics.

### Deliberately NOT moved

Still in the legacy facade/domain side:
- Family create/join/lobby/creation approval;
- Family claiming and join-code flows;
- Family feature overrides and Family experience-level policy;
- Family admin/membership/profile-link operations;
- Family network settings/labels;
- Family members/relationships/governance;
- invitations/contribution/community/groups/events;
- memories/life events/notifications/digest;
- guide feedback;
- S3-A1 Family intake;
- Family community/trust/introductions.

These move only when a capability contract or second consumer proves the semantics.

## Compatibility facade

`lib/remote.ts` remains the import surface used by existing Family code.

G1.4 adds named re-exports from the three capability transport modules instead of forcing callers to change imports. A compatibility snapshot contains all **147 historical G1.3 exports**; `validate:g1.4` fails if any are lost.

Therefore existing code such as:

```ts
import { fetchPlatformLaunchConsole, setActiveNetwork, fetchMyNetworks } from "../lib/remote";
```

continues to work unchanged.

## Dependency guardrails

`validate:g1.4` enforces:
- extracted capability transport cannot import root `verticals/*` implementations;
- neutral network-context transport cannot expose the Family `member_id` link;
- moved RPC implementations no longer live in `lib/remote.ts`;
- representative Family RPCs remain in the legacy facade and were not over-extracted;
- all 147 historical facade exports remain available;
- the G1.3 Playground code↔database catalog-drift protection remains present;
- migration 044 still reconciles every canonical Family feature key.

The G1.3 gate was updated only to follow `fetchMyNetworkMemberships()` into its new capability module. Its architectural assertion is unchanged.
