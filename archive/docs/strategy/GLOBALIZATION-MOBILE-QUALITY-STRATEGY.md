# Generic Network OS — Globalization, Internationalization & Mobile Quality Strategy

**Updated:** 2026-08-27  
**Status:** Product-quality requirement, not an optional feature track.

## 1. Principle

Internationalization, localization, accessibility and mobile portability are **quality gates**. They must not be postponed as cosmetic cleanup after feature work.

The new product rule is:

> Fewer experiences, completely finished across language, screen size and interaction mode.

## 2. Internationalization completion standard

A locale is not “supported” merely because navigation labels translate.

For a supported locale, verify:
- all visible static strings;
- dialogs, validation and errors;
- empty states;
- tooltips/help/guide content;
- Playground/demo content where applicable;
- dates, numbers and relative time;
- emails/invitations/notifications generated by the app;
- dynamic labels from vertical capability definitions;
- accessibility labels;
- server/API surfaced user messages where relevant.

Introduce an **I18N Completeness Gate** that can fail CI when new user-visible literal strings bypass localization in designated product surfaces.

## 3. Locale architecture

Separate:
- interaction locale;
- network default locale;
- content language;
- user/profile preferred language;
- source-language evidence in RAG/knowledge systems.

Never assume one translation choice should mutate stored person/network content.

## 4. Global customization

Use capability/config profiles rather than forks:
- region-aware terminology;
- locale/date/address/phone formatting;
- culturally specific optional features;
- jurisdiction/privacy defaults;
- vertical-specific relationship types;
- feature visibility by network template.

## 5. Mobile-first architecture rule

The web product remains useful, but future components must be designed so the product can move to a native/mobile shell without re-inventing domain logic.

Prefer:
- API/repository-driven domain behavior;
- UI-agnostic TypeScript contracts and graph engines;
- responsive, touch-friendly interaction semantics;
- deep-linkable entity/action routes;
- explicit navigation state rather than DOM assumptions;
- shared design tokens;
- portable validation and permission logic;
- media upload/compression services behind interfaces;
- notification/event contracts independent of browser APIs.

Avoid:
- business logic embedded deeply in React DOM components;
- hover-only critical actions;
- desktop-only oversized tables as the sole interaction;
- browser storage as authoritative persistence;
- functionality dependent on unsupported web-only APIs without an abstraction boundary.

## 6. Future mobile strategy

Do not build native immediately. Prepare for a staged path:

1. **Mobile-quality web/PWA discipline** — all core journeys work cleanly on touch/mobile.
2. **Shared domain package extraction** — graph, permissions, contracts, API client, i18n and vertical schemas reusable outside Next.js UI.
3. **Native shell evaluation** — likely React Native/Expo or another approach based on the codebase at that time.
4. **Lean mobile product** — prioritize daily/primary journeys; do not blindly mirror every admin/web screen.
5. **Native capabilities** — push notifications, camera/media capture, contacts/share integration and offline-friendly selected flows only where valuable.

## 7. Mobile product philosophy

Mobile should contain the **highest-frequency/highest-value actions**, not every screen:
- My Networks / active network;
- search/find person/entity;
- relationship/path/expertise discovery;
- one meaningful moment/request/action;
- notifications/invitations;
- profile/context;
- lightweight contribution/upload;
- vertical-specific urgent workflows.

Heavy configuration, bulk import and deep administration can remain web-first where appropriate.

## 8. Quality gate

A meaningful mission is not experience-complete until checked for:
- desktop;
- tablet;
- mobile web;
- keyboard/accessibility basics;
- all supported locales;
- long translated strings;
- empty/loading/error states;
- future-native portability hazards.
## 9. Mission 1 implementation checkpoint — 2026-08-27

Mission 1 establishes the first enforceable quality slice:

- central i18n catalog keys are type-complete across English/Hindi/Marathi;
- relationship presentation is localized independently of graph/domain labels;
- the Family critical journey (auth/recovery, setup/join/import, signature Home, Tree, Profile, Memories, shell and appearance controls) has an automated source gate;
- untranslated English-only contextual Excel guide content is suppressed in Hindi/Marathi rather than leaked into the localized flow;
- the signature selection model is React/DOM/browser-independent for later native reuse.

This is **not** a claim that every deep Explorer/Admin surface or every non-Family vertical is fully localized. Those remain subject to the same completeness rule before they are marketed as fully supported locales.
