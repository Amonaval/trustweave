# G9.1 RAG × Network OS Integration Hypothesis

## Purpose
This is a **design hypothesis**, not an implementation decision. The next session must inspect the authoritative ZIPs of both products and validate or reject it.

## Why investigate
The current Network OS gains value from structured, verified entities and relationships, but commercial onboarding can become expensive if customers must manually populate and maintain the graph. The existing Knowledge Hub/RAG product may already contain reusable ingestion, retrieval and local-model intelligence capabilities that can convert existing organizational knowledge into evidence-backed candidate graph facts.

Conversely, Network OS can make RAG better by supplying entity resolution, typed relationships, graph paths, ownership/dependency context and deterministic reasoning.

## Candidate combined advantage
**Existing knowledge → evidence → living graph → better questions/decisions → detected gaps → human/network contribution → improved knowledge.**

The bridge is successful only if it:
1. materially reduces data onboarding/maintenance;
2. improves answer accuracy/explainability;
3. reveals risks/gaps not obvious from document search alone;
4. produces actionable workflows;
5. can be piloted without enterprise-scale integration complexity.

## Truth model
- Verified Network OS facts remain governed structured truth.
- RAG/LLM extractions are candidate evidence unless sourced from an explicitly authoritative integration.
- Every promoted relationship should be traceable to provenance.
- Generative models may explain or synthesize evidence; they must not invent graph truth.

## Initial vertical
Organization only. Reassess Franchise after the Organization pilot architecture is proven.

## Decision gate
After inspecting both ZIPs, choose one:
- **PROCEED** — compelling shared engine/service architecture and pilot value;
- **NARROW** — only selected RAG capabilities are worth extracting;
- **REJECT** — integration complexity exceeds customer advantage.

No implementation begins until this decision is made.

## Additional Strategic Role — Network Bootstrap Engine

The integration hypothesis gains an additional role. RAG × Network OS was initially justified for Organizational Intelligence, but the reusable part may later become a **Network Bootstrap Engine**.

Possible inputs by vertical:
- Organization: documents, wikis, architecture, project records;
- Franchise: SOPs, store directories, training/incident records;
- Alumni: rosters, institutional records, profile exports;
- Community: member directories, forms, spreadsheets/documents;
- Family: spreadsheets, distributed intake, structured records.

The first implementation must still remain Organization-focused. Do **not** generalize prematurely. But when selecting extraction boundaries in the next two-ZIP review, prefer contracts that can later support multiple trusted network types without coupling them to Organization semantics.
