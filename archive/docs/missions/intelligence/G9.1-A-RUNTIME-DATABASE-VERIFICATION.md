# G9.1-A Runtime / Database Verification

## Result

**Source/runtime regression gate: PASS.** The G9.1-A gate and the complete chained G9→G8 validation suite pass without coupling G9 deterministic intelligence to the new bridge.

## Security checks now enforced

- all four new evidence tables use RLS;
- only **active** network memberships satisfy ordinary read policies;
- `restricted` knowledge sources/evidence are not exposed through the ordinary member SELECT policy;
- no INSERT/UPDATE/DELETE/ALL client policies are opened in G9.1-A;
- the adapter requires explicit `networkId`, `corpusId`, authenticated principal and authorization references;
- principal/network mismatch is rejected;
- an empty authorization scope is blocked;
- existing G9 deterministic engine/runtime does not import the bridge.

## Database verification

`supabase/verification/g9_1a_database_schema_verification.sql`

It is a read-only catalog verification and raises an exception when the four tables, RLS, active-membership policies, restricted-evidence protection, or closed-write policy state are wrong.

## Real tenant-isolation smoke test

The catalog gate cannot impersonate real Supabase users. Before G9.1-B production use, verify with two actual users/networks:

1. User A is active in Network A; User B is active in Network B.
2. Insert test evidence through an administrator/service context (G9.1-A intentionally exposes no browser write policy).
3. User A can read Network A `visibility='network'` evidence.
4. User A cannot read Network B evidence.
5. User A cannot read `visibility='restricted'` evidence through ordinary table SELECT.
6. Change User A membership to `suspended`; Network A evidence becomes unreadable.
7. Restore the membership after the smoke test.

This final live test requires the project's real Supabase environment and is therefore an environment certification step, not something encoded as a bypassing test RPC.
