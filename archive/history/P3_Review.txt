P3 Architecture + Capability Audit
1. Executive assessment
Current P3 maturity: good functional prototype / early production foundation

I would rate it roughly:

Area	P3 state	Assessment
Core hierarchy visualization	✅ Strong	Good demo/product foundation
Profiles/directory	✅ Strong	Basic but coherent
Search/filter	✅ Good	Works client-side
Lineage focus	✅ Good	Useful differentiator
Map/location	✅ Good	Functional city-level view
Auth	✅ Foundation	Email/password + roles
Supabase persistence	✅ Foundation	Shared canonical backend
RLS	⚠️ Partial	Better than UI-only security, but privacy model incomplete
Relationship management	⚠️ Partial	Basic parent/spouse CRUD only
Profile approvals	✅ Foundation	Functional workflow
Import	✅ Good	Strong UUID/source-ID handling
Data governance	⚠️ Partial	Audit table exists but isn't actually wired
Data quality	❌ Missing	No duplicate/graph validation
Media	❌ Missing	URL-only photos
Notifications	❌ Missing	No event/notification system
Large-scale performance	⚠️ Fragile	Designed around loading entire network
Advanced genealogy	❌ Missing	Not yet a genealogy engine
Extensibility	⚠️ Moderate	Domain is clean, orchestration is too monolithic

So I would not rewrite P3.

The architecture is good enough to become P4, but there are a handful of foundational corrections that should happen before piling on advanced features.

The current architecture is essentially:

Next.js 14
   │
   └── NetworkApp
         │

                │

          lib/ domain/data
                │
         ┌──────┴──────┐
         │             │
      Supabase      localStorage

         ├── profiles
         ├── family_members
         ├── family_relationships

The biggest architectural weakness is that NetworkApp.tsx currently owns almost all application orchestration: hydration, authentication, search, filtering, lineage calculation, imports, approval, relationship mutation, export, view state and modal state.

That is manageable now, but it becomes a bottleneck in P4.

3. Capability audit
A. Hierarchy / graph
Implemented ✅

The application genuinely has a relationship graph rather than merely displaying a list.

It supports:

generation-based tree positioning
parent/child edges
spouse edges
deceased styling
member selection
mini-map
zoom/pan
lineage focus
relationship traversal
siblings derived through common parents.

The tree uses React Flow (@xyflow/react), which is a good choice.

Current model

The core relationship model is:

type RelationshipType = "parent" | "child" | "spouse";

and:

person_id
related_person_id
relationship_type
Partial ⚠️

The relationship model is more limited than the UI makes it appear.

The actual UI only supports:

Parent
Spouse

There is no UI for:

Child
Sibling
Adoptive parent
Step parent
Step child
Guardian
Former spouse
etc.

Also, child exists in the type/database constraint but is effectively not part of the actual authoring workflow.

Fragile ⚠️

The tree layout is generation-based, not relationship-derived.

Nodes are placed roughly as:

generation 1 → y = 55
generation 2 → y = 245
generation 3 → y = 435
...

So the system assumes generation_level is already correct.

That means:

The graph does not yet understand genealogy deeply enough to derive the hierarchy itself.

This becomes important when we introduce editing, imports, merges or complex marriages.

4. Lineage engine
Implemented ✅

This is one of the better parts of P3.

The code calculates:

ancestors
descendants
siblings
spouses

around a selected person and creates a focused subset.

That's already a useful product feature.

Partial ⚠️

It is not yet a general relationship-path engine.

For example, future questions like:

"How is Person A related to Person B?"

or:

"Show the shortest path between A and B"

will need a proper graph traversal layer.

Currently lineage logic lives inline inside NetworkApp.

Recommendation

Promote this into a real domain module:

lib/graph/
   traversal.ts
   lineage.ts
   relationship-path.ts
   validation.ts

That should happen before advanced genealogy functionality.

7. Privacy

This is one of the most important findings.

There is a UI selector:

Preview: Public
View: Member
View: Admin

and ProfileDrawer hides phone/email when Public is selected.

But this is presentation-level privacy, not actual field-level privacy.

The database query fetches the entire approved member record for an authenticated user.

So a normal member receives fields including:

phone
email

from Supabase, and React merely chooses whether to render them.

Therefore:

The current Public/Member/Admin visibility model is not a true privacy boundary.

The good news is that the base RLS architecture is already there.

The migration correctly establishes authenticated access, admin role checking and RLS policies, which is a strong foundation. But the privacy layer needs to be redesigned around what data is actually queryable by each role.

P4 status: 🔴 Must fix before serious community rollout

This is higher priority than fancy features.

8. Authentication / authorization
Implemented ✅

Current system has:

Supabase Auth
    ↓
profiles
    ↓
role = member/admin

and:

signup

signout
first-user admin bootstrap
admin-specific UI
database is_admin() function
admin RLS.

That's a respectable P3 security foundation.

Partial ⚠️

There is no richer permission model yet.

Everything is basically:

member
admin

P4 will likely need:

owner
admin
editor
moderator
contributor
member

or, even better, capability-based permissions.

For example:

can_edit_profile
can_manage_relationships
can_approve_submissions
can_import
can_export
can_view_private_contact

rather than hard-coding role === 'admin' throughout the React code.

11. Import engine

This is actually one of the strongest P3 pieces.

Implemented ✅

The importer handles:

CSV
XLSX
XLS
XML

and importantly:

external/source ID
        ↓
UUID mapping
        ↓
relationship resolution

This directly solves the earlier problem with IDs like:

s1787065934735

being incorrectly inserted into PostgreSQL UUID fields.

The source-ID → generated UUID model is the right direction.

Partial ⚠️

Current import is still fundamentally a load/merge mechanism, not a data-management engine.

It does not provide:

duplicate detection
conflict preview
merge
diff
rollback
validation report
relationship anomaly report
Important technical issue

replaceRelationships() is misnamed.

It does not replace relationships.

It only upserts supplied relationships.

So:

Existing:
A → B
A → C
A → D


Import:
A → B
A → C

does not necessarily mean A → D gets removed.

The UI documentation actually acknowledges this behavior.

That's fine for an additive import, but the function name and product semantics should eventually become explicit:

mergeRelationships()

versus:

replaceRelationships()

19. Major architectural fragility: NetworkApp

This is the biggest code-structure issue.

NetworkApp.tsx currently owns too much.

It contains:

auth
network initialization
remote hydration
local persistence
search
filters
lineage traversal
imports
approval
relationship CRUD
exports
visibility
navigation
modal state
notifications

This won't break at 150 members.

But P4 will become increasingly hard to reason about.

Refactoring target

Move toward:

components/
hooks/
  useAuth.ts
  useNetwork.ts
  useMembers.ts
  useRelationships.ts
  useSearch.ts
  useLineage.ts


lib/
  domain/
    graph.ts
    lineage.ts
    validation.ts
    matching.ts


repositories/
  network-repository.ts
  supabase-repository.ts
  local-repository.ts

Then NetworkApp becomes mostly composition.

Do not rewrite now.
Extract incrementally as P4 features touch each area.

25. Bottom line

The good news is:

P3 is not a throwaway prototype.

The core architecture is actually good enough to evolve.

The strongest existing pieces are:

✅ React Flow graph
✅ Supabase persistence
✅ RLS foundation
✅ role model
✅ source-ID → UUID import
✅ profile submission workflow
✅ deterministic demo data
✅ generic network abstraction
✅ lineage focus
✅ location model

The things I would fix before major feature expansion are:

🔴 privacy enforcement
🔴 relationship/data validation
🔴 real audit logging
🔴 server-side scalable discovery
🟠 change-request architecture
🟠 relationship model expansion
🟠 repository/domain separation

And the most promising actual P4 feature is, in my view:

Turn the hierarchy from a visual tree into a relationship intelligence system — where users can discover paths, understand connections, maintain trustworthy data, and progressively build a living history around each person.

That direction fits the P3 architecture extremely well without forcing a rewrite.
