# P4.2 — Relationship Intelligence & Human Profiles

P4.2 is built directly on the P4.1 source baseline.

## Implemented

### Relationship intelligence
- Shortest graph path between two members.
- Plain-language relationship explanation for direct parent/child/spouse links.
- Blood-relationship interpretation for siblings, aunt/uncle, niece/nephew and cousins with removal.
- Common ancestor discovery.
- Common descendant discovery.
- Generation/path distance.
- Clickable path members and profile navigation.
- Existing lineage focus remains unchanged.

### Human profile evolution
- Simple life-event timeline.
- Event types: birth, marriage, move, education, career, family, milestone, other.
- Event title, date, location, description and visibility.
- No LinkedIn-style structured career/education model.
- Existing profile photo, bio and contact fields remain.

### Profile privacy
- Profile visibility: all members / members / admins only.
- Contact visibility: members / admins only.
- Database RPC redacts restricted profile details before they reach the browser.
- Timeline events have their own visibility.

### Mobile
- Existing P4.1 bottom navigation retained.
- Relationship explorer, timeline and profile editing use responsive layouts.
- P4 features remain mobile-usable as they are introduced.

## Supabase migration

For an existing P4.1 database, run:

`supabase/migrations/007_p4_2_relationships_profiles.sql`

It adds profile visibility fields, life events, visibility-aware member retrieval and secure life-event RPCs.

## Validation

The relationship intelligence engine was compiled independently with TypeScript and exercised against a small synthetic hierarchy covering sibling, cousin and spouse-connected paths.

A full Next.js dependency install/build was not available in the isolated execution environment, so production build validation must still be run after `npm install` in the project environment.


## P4.2 migration compatibility note

Migration 005 grants SELECT on `family_members` to `authenticated` but keeps its direct SELECT RLS policy admin-only. This is required by PostgREST for admin PATCH/UPSERT operations that may need to read the affected row. Normal members continue to receive family-member data only through `get_visible_family_members()`, which redacts protected fields.
